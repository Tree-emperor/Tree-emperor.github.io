一、短信登录

这里主要有2个地方用到redis：

  1. redis中验证码是string存储：<phone,code>
  2. redis中用户是hash存储：<token，user对象>

主要有2部分要实现：

  1. 短信验证码注册、登录
  2. 校验登录状态

下面详细介绍这两部分。

Ⅰ 短信验证码注册、登录

首先验证码存储很简单，就是以电话号为key，随机生成验证码，以<phone,code>形式存入redis，难点在于怎么把用户存入redis。

如果使用传统的session登录，由于session不适合集群模式，就是好几个tomcat服务器，运行时采用轮询策略，每个请求处理的服务器不同，不可能每个服务器都存一份session的用户数据，同份数据存多次，既造成了访问延迟数据更新不及时，也造成了内存浪费。

那么用redis存储，key选什么呢？这里选择token，因为登录操作后续肯定和拦截器有关的，所以用token作为key，既能区分不同用户，又能避免电话号做key可能导致的电话号泄露安全隐患。 也就是redis中用户是hash存储：<token，user对象>

Ⅰ缓存更新策略

首先要知道缓存的是啥玩意，缓存的是商家信息，redis中用string形式:<商铺id，商铺（shop对象转换为json字符串）>

这里有一个小细节，以后可以用到： 凡是以id为key的，都可以在前面加个字符串标识，这样在redis中容易区分key。 如这里key为：“cache:shop:” + shop.getId()；

更新缓存时，重点在于保证数据的一致性，也就是缓存和数据库内容得一致，这就又引出了2个问题：

  1. 更新缓存还是删除缓存？ 答：选择删除缓存。即：更新数据库时让缓存失效，查询时再更新缓存； 这种操作比更新数据库时更新缓存更好，减少了很多无效读写。

  2. 先操作缓存还是先操作数据库？ 答：这里要选择先操作数据库，后删除缓存操作。相比之下，这种操作发生数据不一致的概率极低，下面详细介绍在多线程并发情况下，两者的数据不一致可能。

Ⅱ缓存穿透

缓存穿透是指客户端请求的数据在缓存中和数据库中都不存在，这样缓存永远不会生效，这些请求都会打到数据库。 如果有个坏人一直请求这种不存在的数据，就会把所有请求打到数据库，这样数据库的压力非常大，因此要解决缓存穿透问题。

常见解决方案有2种：缓存空值或布隆过滤器，如下图。其中布隆过滤器这里没实现，就主要考虑缓存空值操作：

简介一下缓存雪崩：

缓存雪崩是指在同一时段大量的缓存key同时失效或者Redis服务宕机，导致大量请求到达数据库，带来巨大压力。 解决方案： 给不同的Key的TTL添加随机值 利用Redis集群提高服务的可用性 给缓存业务添加降级限流策略 给业务添加多级缓存

/**  
 * 获取锁  
 *  
 * @param key  
 * @return boolean  
 */
 private boolean tryLock(String key) {  
    //setIfAbsent在不存在时才创造，也就是redis中的setnx命令，实现了互斥  
    //并且给定有效期，避免出问题没人释放锁  
    Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", LOCK_SHOP_TTL, TimeUnit.SECONDS);  
    //避免自动拆箱引发空指针异常  
    //即避免Boolean转boolean出现空指针  
    return BooleanUtil.isTrue(flag);  
}  
  
/**  
 * 释放锁  
 *  
 * @param key  
 */  
private void unLock(String key) {  
    stringRedisTemplate.delete(key);  
}

/**  
 * 互斥锁解决缓存击穿  
 * 这里的🔒是redis里的锁，lockKey；不同于shopKey！  
 * @param id id  
 * @return {@link Shop}  
 */
 private Shop queryWithMutex(Long id) {  
    String shopKey = CACHE_SHOP_KEY + id;    //从redis中查询  
    String shopJson = stringRedisTemplate.opsForValue().get(shopKey);    
    //判断是否存在  
    if (StringUtils.isNotEmpty(shopJson)) {        
    //存在直接返回  
        return JSONUtil.toBean(shopJson, Shop.class);    
        }    
        //缓存命中，且为空值，直接返回null ！！！处理缓存穿透！！！  
    if ("".equals(shopJson)) {        
	    return null;    
	    }    
    //实现缓存重建  
    //获取互斥锁  
    String lockKey = LOCK_SHOP_KEY + id;    
    Shop shop = null;    
    // ctrl + alt + t    
    // 当try、catch中有return时，也会执行finally,所以释放锁写入finally
    try {        
    boolean isLock = tryLock(lockKey);        
    //是否获取成功  
        if (!isLock) {            
        //获取失败 休眠并且重试（递归实现）  
            Thread.sleep(50);            
            return queryWithMutex(id);        
            }        
            //成功 通过id查询数据库  
        shop = getById(id);        
        //模拟重建延时，方便本地测试  
        Thread.sleep(200);        
        if (shop == null) {            
        //redis写入空值  ！！！处理缓存穿透！！！
            stringRedisTemplate.opsForValue().set(shopKey, "", CACHE_NULL_TTL, TimeUnit.MINUTES);            
            //数据库不存在 返回错误  ！！！处理缓存穿透！！！
            return null;        
            }        
            //数据库存在 写入redis  
        stringRedisTemplate.opsForValue().set(shopKey, JSONUtil.toJsonStr(shop), CACHE_SHOP_TTL, TimeUnit.MINUTES);    
        } catch (InterruptedException e) {        
	        throw new RuntimeException(e);    
        } finally {        
        //释放互斥锁  
        unLock(lockKey);    
        }    
        //返回  
    return shop;
 }

快捷键知识2：ctrl + alt + t快捷键选中代码使用try{…}catch{…}来检查异常，也可以用于在外面套一层for、if等，最常用的还是try-catch。

总结：用互斥锁可以保证一致性，但是线程等待浪费性能，还要小心死锁问题。

②逻辑过期解决缓存击穿

基本思路说白了就是：

热点key实际上没设置过期时间，也就是说你访问必命中。但是会额外存一个expire值，这个值是一个时间戳。 当访问到热点key，必命中，取出value后，检查expire时间戳，如果过期了，加互斥锁，然后新开一个线程t，让这个线程t去进行缓存重构等业务。（也就是所谓的异步操作） 如果此时又来了其他线程，缓存还没重构好，那就直接让其他线程返回已经逻辑过期的值。 可以看出来这种方式其实不是很严格。如果你可以接受用户看到个过期的数据，没啥影响，可以用这种方式，因为这种方式线程不用等待，性能很好。如图：

这里注意点很多：

  1. 提前把热点key存入redis 这是逻辑过期实现的基础。一定要把热点key提前存入redis，后续进行才不会出错！！

  2. 缓存穿透问题怎么解决？ 答：正常缓存穿透问题如果缓存没访问到，要访问数据库，如果数据库也访问不到，就要缓存空值了。 但是逻辑过期方案由于已经提前把热点key存入redis了，而且这个key没有过期时间，就导致如果缓存没访问到，那说明数据库一定也不存在这个值！就不用访问数据库了，直接返回null。 换句话说，这种情况下不会再出现缓存穿透问题！

  3. 如何给value额外加一个expire属性？ 答：这里可以使用装饰者模式。

  4. 如何新开一个线程操作？ 答：这里用Java线程池，没学过后面会说。

Ⅰ全局唯一ID

每个店铺都可以发布优惠券。当用户抢购时，就会生成订单并保存到tb_voucher_order这张表中，而订单表如果使用数据库自增id就存在一些问题：

  • id的规律性太明显
  • 受单表数据量的限制

如果有个坏人知道了接口格式，发现id规律性太明显了，就可以利用id规律做坏事了。 我们希望能有一个唯一且自增长的id，为了增加id的安全性，我们可以不直接使用Redis自增的数值，而是拼接一些其它信息：

id的组成部分：

  • 符号位：1bit，永远为0
  • 时间戳：31bit，以秒为单位，可以使用69年（这里用于确保安全性，让人不那么容易看出来id的规律）
  • 序列号：32bit，秒内的计数器，支持每秒产生2^32个不同id（这里用于实现自增长，确保id自增长这个特性不变）

可以看出，每秒对应的时间戳不同，也就可以区分id；如果一秒内下多单，这时序列号就起作用了，序列号自增长，保证一秒内的多单也是不同的，也能区分id。

在实现时，时间戳timestamp和序列号count都是long型，这样在数据库中查找速度快。 而且时间戳和序列号我们是分开求的，最后拼接时间戳和序列号作为id即可。

问题又来了：由于序列号是自增（和时间戳分开求，所以二者无关），序列号最多有2^32位，也就是42亿多。假如这个项目很火，运行了好久好久，在漫长的时间长河面前，42亿也挡不住，也就是说序列号迟早会爆，这怎么办？

1.解决序列号迟早会爆的问题

不妨先想想目前序列号如何实现？ 其实是redis自增长实现的，也就是redis的string类型<icr:key前缀（不同问题前缀不同）：，value >，这个value就是序列号count。

我们可以这样实现，假设今天日期为：yyyyMMdd，然后redis存储设置为： <icr:key前缀（不同问题前缀不同）：yyyyMMdd，value >

因为第二天的yyyyMMdd和前一天不同，导致每天的key不同，这样做就导致第二天再自增长时，value重新从0开始了。 通过这样做，只需要保证每天的序列号增长不超过42亿即可，具体来说，保证每天的优惠券不超过42亿张，这显然合理。

2.如何拼接时间戳和序列号

从id的组成成分可知，相当于高32位是时间戳，低32位是序列号。 拼接很简单，让时间戳先左移32位，这时低32位都是0，然后和序列号按位或（也可以直接加序列号来实现）。

@Component  
public class RedisIdWorker {  
    /**  
     * 初始时间戳  
     */  
    private static final Long BEGIN_TIMESTAMP = 1640995200L;  
    /**  
     * 序列号位数  
     */  
    private static final Integer COUNT_BITS = 32;  
  
    @Resource  
    private StringRedisTemplate stringRedisTemplate;  
  
    /**  
     * 获取id  
     * 这个自增长很细节，如果不加today，那就是让key为"icr:" + keyPrefix + ":"的value一直++；迟早会超过32位上限；  
     * 这里加了today，那就每天有一个不同的key（用每天的日期区分）；  
     * 这样只要保证一天内id不超过32位上限（即42亿多）就可以；  
     * @param keyPrefix KEY前缀  
     * @return {@link Long}  
     */    
     public Long nextId(String keyPrefix) {  
        //生成时间戳。这里思路是当前时间-固定时间 = 最终想要的时间戳秒数  
        LocalDateTime now = LocalDateTime.now();  
        long nowSecond = now.toEpochSecond(ZoneOffset.UTC);  
        long timestamp = nowSecond - BEGIN_TIMESTAMP;  
        //生成序列号  
        //生成当前日期 精确到天  
        String today = now.format(DateTimeFormatter.ofPattern("yyyyMMdd"));  
        //自增长  redis自增长命令
        Long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + today);  
        //拼接并返回  先向左移32位，那么低32位全为0，跟序列号进行或操作 
        return timestamp << COUNT_BITS|count ;  
    }  
  
}

这个锁有以下几个问题需要解决：

  1. 锁谁？ 请看前面秒杀优惠券的最基础的代码。

我们要实现的是一人一单，当然要锁userId了，确保同一个userId不能同时访问。

然而没那么简单，userId是Long类型，Java 对 Long 对象有缓存优化（缓存范围为 -128 到 127）。所以如果userId超过这个范围，每个线程持有的 Long 对象地址不同，这样的话锁的不是同一个对象，锁失败！所以要把userId转为String类型。

问题又来了，userId.toString()底层是在new一个String对象，每次调用都会有一个新的String对象，还是没锁到同一个对象;

所以要锁userId.toString().intern()，intern()实现去字符串常量池中找到和你预想的值的一样的地址返回，这样才真正锁上了同一用户！（jvm的知识）

如果锁加在getResult()上，所有访问这个函数的都阻塞，那就不是一人一单了，此时锁的颗粒度太粗，不妥；

如果锁加在getResult()内部的userId上，由于事务的存在，会导致getResult()执行结束后先释放锁后提交事务，换句话说释放锁之前数据库可能没更新，那锁了个寂寞，此时锁的颗粒度太细，不妥；

所以要在seckillVoucher内部先加锁userId，再调用getResult，getResult执行结束后提交事务，此时释放锁即可。实现了先提交事务后释放锁。

满足分布式系统或集群模式下多进程可见并且互斥的锁，核心是实现多进程之间互斥。

这里自然是用redis实现了，那么这个分布式锁其实和前一章用redis实现的互斥锁一样，这里正式讲解思路：

/**  
 * 简单的redis分布式锁  
 *  
 * @author CHEN  
 * @date 2022/10/09  
 */public class SimpleRedisLock implements ILock {  
    private String name;  
    private StringRedisTemplate stringRedisTemplate;  
    private static final String KET_PREFIX="lock:";  
    //注入
    public SimpleRedisLock(String name, StringRedisTemplate stringRedisTemplate) {  
        this.name = name;  
        this.stringRedisTemplate = stringRedisTemplate;  
    }  
  
    @Override  
    public boolean tryLock(Long timeoutSec) {  
        String threadId = Thread.currentThread().getId() + "";  
        //获取锁  
        //这里用redis实现锁，<lock:order:userId,线程id>  
          
        Boolean isSuccess = stringRedisTemplate  
                .opsForValue()  
                .setIfAbsent(KET_PREFIX + name  
                        , threadId  
                        , timeoutSec  
                        , TimeUnit.SECONDS);  
        //避免自动拆箱引发空指针异常  
        //即避免Boolean转boolean出现空指针  
        return Boolean.TRUE.equals(isSuccess);  
    }  
  
    @Override  
    public void unLock() {  
            stringRedisTemplate.delete(KET_PREFIX + name);               
    }  
}

4.2误删问题

上述的初级分布式锁可能会出问题。如果线程1拿到锁之后因为某些原因阻塞了，锁超时释放后，线程2轻松拿到锁，执行过程中线程1不阻塞了，线程1释放锁时由于毫无限制，此时相当于把线程2的锁释放了。此时线程3再来拿锁又轻松拿到，如果线程2还未执行完，相当于线程2、3都拿到了锁，又会出现并发安全问题：

综上所述，显然问题在于释放锁毫无限制，可能会把别人的锁释放了，导致误删问题。

解决方法自然是释放锁时判断一下线程id是不是自己，是自己才可以释放。

当然，集群下，不同的jvm可能会有重复的线程id，所以单纯的判断id还不够，这里判断uuid-id，用以区分不同线程。

在集群环境下，不同JVM实例生成相同UUID的可能性几乎为零，可以认为是安全的；

这里把uuid设置为类级别的变量（类成员变量），在同一个 JVM 进程内，所有线程共享同一个类加载器，因此 uuid 的值在进程生命周期内是固定且唯一的。 这样就实现了同一个jvm进程内，用线程id区分不同线程；不同jvm进程内，用uuid区分不同线程。

4.3原子性问题

上述操作看上去没问题，实则还是有问题。我们看unLock()函数，内部做了2个操作，先获取锁中标识，再释放锁。

由于这两个操作不是原子性的，如果获取锁中标识后，线程又因不可抗力阻塞了（比如赶巧碰上了jvm垃圾回收，jvm的fullgc会阻塞进程）。当线程恢复时，直接就释放锁了，显然，这可能会出现问题：

问题解决方案自然是把这2个操作变成原子性的了，怎么做呢？这里要引入一个新的语言：lua语言。 这是一个基于c语言编写的脚本语言，经常在游戏开发中作为脚本，教程： Lua 教程 | 菜鸟教程

Lua本身不具备原子性的，是因为redis执行命名是单线程执行的，它会把Lua脚本作为一个命令执行，会阻塞期间接收到其他线程命令，这就保证了Lua脚本的原子性。 我们将释放锁的操作写到Lua脚本中去，直接调用脚本。

释放锁的业务逻辑是这样的：

①获取锁中的线程标示

②判断是否与指定的标示（当前线程标示）一致

③如果一致则释放锁（删除）

④如果不一致则什么都不做

4.4Redisson分布式锁

不是哥们你还写上分布式锁了，这么伟大的东西早就有人造好轮子了：

Redisson 是一个在 Redis 的基础上实现的 Java 驻内存数据网格 。 它不仅提供了一系列的分布式的 Java 常用对象，还提供了许多分布式服务，其中就包含了各种分布式锁的实现。 GitHub 地址：https://github.com/redisson/redisson

当然了，用谁不会用啊，学会思想才是最重要的~~

我们先看看我们的setnx实现的分布式锁存在哪些问题： 1.不可重入：同一个线程无法多次获取同一把锁 2.不可重试：获取锁只尝试一次就返回 false，没有重试机制 3.超时释放：锁超时释放虽然可以避免死锁，但如果是业务执行耗时较长，也会导致锁释放，存在安全隐患 4.主从一致性：如果 Redis 提供了主从集群，主从延同步在延迟，当主机宕机时，如果从机同步主机中的数据，则会出现锁失效

接下来分别介绍Redisson实现的原理。

4.4.1可重入性

为什么要可重入呢？可以类比操作系统的读者写者机制，如果两个线程都只是想读一个资源，那就没必要把读者拒之门外了，这时最好是可重入的。

首先利用redis的hash结构，field位置放线程id，value位置记录重入次数。 然后类比操作系统的信号量机制，当value = 0时才释放锁！

4.4.2锁重试和超时续约机制

  • 可重试：利用信号量和PubSub（订阅释放）功能实现等待、唤醒，获取锁失败的重试机制；
  • 超时续约：利用watchDog，每隔一段时间（releaseTime / 3），重置超时时间；
  • leastTime：leastTime是锁失效自动释放的时间，如果给定了值，那么就会在这个时间后自动释放锁，如果不给定，看门狗会自动循环续期过期时间；
  • waitTime：waitTime是等待时间，这个时间内没有获取锁就不等待了，和上一个值不一样；
  • ttl：ttl表示获取已有锁的过期时间，null表示当前没有已存在的锁，即可以成功获取锁；

基于上述参数和下图，介绍一下Redisson分布式锁原理：

①Redisson内部要先执行一个lua脚本，这个lua脚本就是在获取锁，基本思路就是：

如果锁不存在，就让锁存在（value+1）；如果锁存在，并且是我的id，就让锁value+1；这两种情况返回null，代表获取锁成功；
如果锁存在，但不是我的id，返回这个锁的剩余时间，同时也说明获取锁失败。

②针对获取锁脚本返回的结果，如果不为null，恭喜你获取锁失败，此时就要等待锁，这里要判断剩余等待时间，如果不大于0，剩余等待时间不足，直接获取锁失败。如果大于0，订阅这个锁并等待释放的信号，如果来信号了，判断目前为止花了这些时间有没有超过预期规定的waitTime，超过，说明预期时间内没有拿到锁，失败；不超过，说明目前既有释放锁的信号，又有预期时间去获取锁，那就再次尝试获取锁，也就是循环。

③针对获取锁脚本返回的结果，如果为null，恭喜你获取锁成功，此时判断leastTime是否给定了值，如果给定了值，那么就会在这个时间后自动释放锁，如果不给定，看门狗会自动循环续期过期时间；

④释放锁也有可能失败，比如宕机了，看门狗死了，锁提前释放过了，再释放就失败了，反正失败了直接返回就行。如果释放锁成功，先发布消息，然后取消看门狗的循环（也就是不让锁一直续期有效时间）

4.4.3主从一致性

原理：多个独立的 Redis 节点，必须在所有节点都获取重入锁，才算获取锁成功。

Ⅴ秒杀优化

为避免所有操作都在数据库上执行，分离成两个线程，一个线程判断用户的购买资格，发现用户有购买资格后再开启一个独立的线程来处理耗时较久的减库存、写订单的操作。

同步实现时：判断是否有资格，有资格就去操作数据库（扣减库存等），全完事才返回用户下单成功，I/O操作很费时间；

异步实现思路：判断是否有资格，有资格立刻返回给用户，这样用户不需要等太长时间，然后阻塞队列里放一个操作数据库的任务；

  • Spring容器初始化后就开始循环遍历阻塞队列，没有就阻塞，直到有任务，在后台去做操作数据库的任务；
  • 注意：这里是新开了1个线程去异步完成任务，相当于开了个主线程的子线程去做费时的I/O操作；
  • 单线程处理天然满足：订单创建顺序性、避免库存超卖（配合数据库事务）
  • 这样做实现了用户有资格立刻返回，响应速度快，至于费时的数据库操作，后台慢慢做，不着急~

                    .setSql("stock=stock-1"));  
    //创建订单  
    this.save(voucherOrder);  
}

private static final ExecutorService SECKILL_ORDER_EXECUTOR = Executors.newSingleThreadExecutor();  
  
/// Spring容器初始化后执行  
@PostConstruct  
private void init() {  
    SECKILL_ORDER_EXECUTOR.submit(() -> {  
        String queueName = "stream.orders";  
        while (true) {  
            try {  
                //从消息队列中获取订单信息,>代表最近未被消费的 
                //XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS streams.orders >  
                List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(  
                        Consumer.from("g1", "c1")  
                        , StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2))  
                        , StreamOffset.create(queueName, ReadOffset.lastConsumed())  
                );  
                //判断消息是否获取成功  
                if (list == null || list.isEmpty()) {  
                    //获取失败 没有消息 继续循环  
                    continue;  
                }  
                //获取成功 解析消息，明确知道只有一条消息（COUNT 1），所以get(0)  
                MapRecord<String, Object, Object> record = list.get(0);  
                Map<Object, Object> values = record.getValue();  
                //map转voucherOrder  
                VoucherOrder voucherOrder = BeanUtil.fillBeanWithMap(values, new VoucherOrder(), true);  
                //下单  
                handleVoucherOrder(voucherOrder);  
                //ack确认消息 SACK stream.orders g1 id                stringRedisTemplate.opsForStream().acknowledge(queueName, "g1", record.getId());  
            } catch (Exception e) {  
                e.printStackTrace();  
                //如果处理消息时出现异常导致没有被ack确认，此时进入pending list，处理list中的消息  
                handlePendingList();  
            }  
        }  
    });  
}  
  
/**  
 * 处理未被ack确认的异常消息  
 * pendinglist 被对应组读取后才会被添加，使用 xack 确认后才移出  
 */  
private void handlePendingList() {  
    String queueName = "stream.orders";  
    while (true) {  
        try {  
            //从pendinglist中获取订单信息  
            //XREADGROUP GROUP g1 c1 COUNT 1  STREAMS streams.orders 0  
            //区别：不阻塞了，0代表读的是pendinglist里的消息  
            List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(  
                    Consumer.from("g1", "c1")  
                    , StreamReadOptions.empty().count(1)  
                    , StreamOffset.create(queueName, ReadOffset.from("0"))  
            );  
            //判断消息时候获取成功  
            if (list == null || list.isEmpty()) {  
                //获取失败 没有消息 继续循环  
                break;  
            }  
            //获取成功 解析消息  
            MapRecord<String, Object, Object> record = list.get(0);  
            Map<Object, Object> values = record.getValue();  
            VoucherOrder voucherOrder = BeanUtil.fillBeanWithMap(values, new VoucherOrder(), true);  
            //下单  
            handleVoucherOrder(voucherOrder);  
            //ack确认消息  
            stringRedisTemplate.opsForStream().acknowledge(queueName, "g1", record.getId());  
        } catch (Exception e) {  
            e.printStackTrace();  
            try {  
                Thread.sleep(20);  
            } catch (InterruptedException ex) {  
                throw new RuntimeException(ex);  
            }  
        }  
    }  
}

Ⅱ关注推送

这个还算有用。关注推送也叫做 Feed 流，直译为投喂。为用户持续的提供 “沉浸式” 的体验，通过无限下拉刷新获取新的信息。

Feed 流产品有两种常见模式：

  • Timeline：不做内容筛选，简单的按照内容发布时间排序，常用于好友或关注。

例如朋友圈

优点：信息全面，不会有缺失。并且实现也相对简单 缺点：信息噪音较多，用户不一定感兴趣，内容获取效率低

  • 智能排序：利用智能算法屏蔽掉违规的、用户不感兴趣的内容。推送用户感兴趣信息来吸引用户

例如抖音，快手

优点：投喂用户感兴趣信息，用户粘度很高，容易沉迷 缺点：如果算法不精准，可能起到反作用

本例中的个人页面，是基于关注的好友来做 Feed 流，因此采用 Timeline 的模式。 该模式的实现方案有三种：拉模式、推模式、推拉结合

模式介绍

拉模式：也叫做读扩散
粉丝有个收件箱，每次要读收件箱的时候从博主的发件箱中获取消息，内存消耗小，但读操作过于频繁，若用户关注了许多博主，一次要读的消息也是十分多，造成延迟较高。

推模式：也叫做写扩散。
发消息时博主直接写入粉丝收件箱，内存占用更高，写操作频繁，若博主有许多粉丝，写操作更加繁重。

推拉结合模式：也叫做读写混合，兼具推和拉两种模式的优点。
普通博主，粉丝少，可以采用推模式，写操作并不是很繁重
大v博主，粉丝多；分两种粉丝，活跃粉，普通粉；活跃粉，数量少，可以采用推模式；普通粉，数量多，但上线查看少，采用拉模式，什么时候看什么时候拉取。

代码实现-推模式

这里用推模式实现关注推送。

Feed 流中的数据会不断更新，所以数据的角标也在变化，因此不能采用传统的分页模式。所以要实现滚动分页，这种情况下又要排序，所以使用sortedSet来实现收件箱。

如果是按角标分页：ZRANGE key beginIndex, endIndex，如果此时插入新的元素，下一页查询会出问题。也就是某些传统网站，你跳到下一页也会展示出一些前一页的数据。

滚动分页：ZREVERSERANGEBYSCORE key max min LIMIT offset count，说白了就是记录一下这一页最小的分数，查下一页时，要求下一页的分数低于前一页的最小值（假设按倒序排列）。

这里的max就是上一次查询时最小的分数； limit是≤； offset是从小于等于最大值的第几个元素开始； count代表查几个；

具体来说，max代表上一次查询时最小的时间戳，由于可能有重复元素，offset设定为上一次查询的最小的分数中，重复了几个，就1+几。会有bug：当重复数据超过2*count时会死循环；

这个命令最后可以解析出3种数据：blogId minTime（时间戳） offset，其中blogId 就是我们需要的（用来展示博客），剩下2个值用于下次查询，所以在获得blogId 、装入ids时，同时更新minTime（时间戳） offset。

/**  
 * 滚动分页查询收件箱，这里利用时间戳作为排序，count代表一页展示几个，这里为2；  
 * 基本思路：  
 * max是上一次查询时的最小分数，用minTime接收；  
 * offset用os接收，这里设定为上一次查询的最小的分数中，重复了几个，就1+几。会有bug：当重复数据超过2*count时会死循环；  
 * @param max    最大值  
 * @param offset 偏移  
 * @return  
 */  
@Override  
public Result queryBlogOfFollow(Long max, Integer offset) {  
    //获取当前用户  
    UserDTO user = UserHolder.getUser();  
    //查询收件箱  
    //ZREVERSERANGEBYSCORE key max min LIMIT offset count  
    //这里得到的结果会按照时间戳降序排列  
    String key="feed:"+user.getId();  
    Set<ZSetOperations.TypedTuple<String>> typedTuples = stringRedisTemplate.opsForZSet()  
            .reverseRangeByScoreWithScores(key, 0, max, offset, 2);  
    //非空判断  
    if (typedTuples==null||typedTuples.isEmpty()){  
        return Result.ok();  
    }  
    //解析数据 blogId minTime（时间戳） offset    
    List<Long> ids = new ArrayList<>(typedTuples.size());  
    long minTime =0;  
    int os=1;  
    for (ZSetOperations.TypedTuple<String> typedTuple : typedTuples) {  
        //封装blogId
        ids.add(Long.valueOf(typedTuple.getValue()));  
        long time = typedTuple.getScore().longValue();  
        //offset计算，上一次查询的最小数据重复就++  
        if (time==minTime){  
            os++;  
        }else {  
            //如果不重复了，重新赋值最小分数和offset  
            minTime = time;  
            os=1;  
        }  
    }  
    //循环查询blog，这里没有用批量查询，批量查询mp又要改。
    //根据blogId封装blog
    //blog还要封装是否点赞，这个容易忘  
    List<Blog> blogs=new ArrayList<>(ids.size());  
    for (Long id : ids) {  
        Blog blog = getById(id);  
        blogs.add(blog);  
    }  
    blogs.forEach(this::isBlogLiked);  

	
    //拿到blogs、offset、minTime返回给前端
    // blogs用于展示，offset、minTime用于查下一页
    ScrollResult scrollResult = new ScrollResult();  
    scrollResult.setList(blogs);  
    scrollResult.setOffset(os);  
    scrollResult.setMinTime(minTime);  
    return Result.ok(scrollResult);  
}

        //判断是否需要坐标查询

        String key= SHOP_GEO_KEY+typeId;

        Point point = new Point(x, y);

        Circle searchCircle = new Circle(point, new Distance(5000));

        GeoResults<RedisGeoCommands.GeoLocation<String>> results = stringRedisTemplate.opsForGeo().  
                radius(key,  
                        searchCircle,  
                        RedisGeoCommands.GeoRadiusCommandArgs  
                                .newGeoRadiusArgs()  
                                .includeDistance()  
                                .limit(end)          // 结果数量限制  
                );

//                .search(key

//                        , new Distance(5000)  
//                        , RedisGeoCommands.GeoSearchCommandArgs.newGeoSearchArgs().includeDistance().limit(end)  
//                );  
        //解析出shopId  
        if (results==null){  
            return Result.ok(Collections.emptyList());  
        }  
        List<GeoResult<RedisGeoCommands.GeoLocation<String>>> content = results.getContent();  
        if (content.size()<from){  
            //没有下一页  
            return Result.ok();  
        }  
        //截取from~end部分，用content.stream().skip(from)实现  
        //distanceMap是为了id和distance一一匹配，一起返回

        for (Shop shop : shopList) {

        }  
        return Result.ok(shopList);

七、用户签到

这里使用位图实现用户签到。分为以下3部分：

  1. BitMap
  2. 签到
  3. 签到统计

ⅠBitMap

我们按月来统计用户签到信息，签到记录为 1，未签到则记录为 0。把每一个 bit 位对应当月的每一天，形成了映射关系。用0和1标示业务状态，这样一个月也只消耗31位（4字节）这种思路就称为位图（BitMap）；类似于操作系统文件管理的位图表。

Redis 中 是利用 string 类型数据结构实现 BitMap，因此最大上限是 512M，转换为 bit 则是 2^32个 bit 位。

redis中BitMap主要有需要1个参数：offset代表指定位置； 由于是针对月份签到，设置key为：USER_SIGN_KEY +yyyyMM+ 登录用户id;

        LocalDateTime now = LocalDateTime.now();

        String format = now.format(DateTimeFormatter.ofPattern(":yyyyMM"));

        //获取今天是本月的第几天

        List<Long> result = stringRedisTemplate.opsForValue().bitField(
                key,
                BitFieldSubCommands.create()
                        .get(BitFieldSubCommands.BitFieldType.unsigned(dayOfMonth)).valueAt(0)
        );
        if (result == null || result.isEmpty()){
            //没有任何签到结果
            return  Result.ok(0);
        }
        //所以用get(0)取出结果
        Long num = result.get(0);
        if (num == null || num == 0){
            return Result.ok(0);
        }
        //转二进制字符串  
		String binaryString = Long.toBinaryString(num);  
		//计算连续签到天数  
		int count=0;  
		for (int i = binaryString.length()-1; i >=0; i--) {  
		    if (binaryString.charAt(i)=='1'){  
		        count++;  
		    }  
		    else {  
		        break;  
		    }  
		}
        return Result.ok(count);
    }

八、UV统计

UV：全称 Unique Visitor，也叫独立访客量，是指通过互联网访问、浏览这个网页的自然人。1 天内同一个用户多次访问该网站，只记录1次。

PV：全称Page View，也叫页面访问量或点击量，用户每访问网站的一个页面，记录 1 次PV，用户多次打开页面，则记录多次PV。

往往用来衡量网站的流量。

Hyperloglog（HLL）是从 Loglog 算法派生的概率算法，用于确定非常大的集合的基数，而不需要存储其所有值。

相关算法原理大家可以参考：https://juejin.cn/post/6844903785744056333#heading-0

Redis 中的 HLL 是基于 string 结构实现的，单个 HLL 的内存永远小于 16 kb，内存占用低，但相对的其测量结果是概率性的，有小于 0.81％ 的误差。不过对于 UV 统计的庞大数量来说，这完全可以忽略。

总结：

  • HyperLogLog 的作用：做海量数据的统计工作

  • HyperLogLog 的优点：内存占用极低、性能非常好

  • HyperLogLog 的缺点：有一定的误差
